01 / Executive summary

Strong product code, unsafe production controls.

The repository can produce deployable artifacts, but it has release-blocking security defects and no repository-enforced delivery gate. Production readiness is blocked by authorization, dependency risk, and deployment drift, not by basic compilation.

P0

Tenant data is not protected consistently

Several public Convex queries and mutations do not authenticate the caller or verify access to the target team/project. The exposed surface includes project listing and destructive project mutations, inventory, lab reports, comments, recipe subdocuments, equipment, and step dependencies.

Evidence: convex/projects.ts, convex/inventory.ts, convex/labReports.ts, convex/comments.ts

P0

Production dependencies have known vulnerabilities

pnpm audit --prod reports 27 vulnerabilities: 2 critical, 16 high, 7 moderate, and 2 low. Direct Better Auth 1.5.3 is below patched versions listed by multiple advisories; a critical tar issue is also present through the Nuxt server dependency tree.

Evidence: rd/formulation-lab/package.json, pnpm-lock.yaml · command exit 1 on 2026-08-01

02 / Release blockers

Fix these before any customer data enters the system.

These findings can cause cross-tenant disclosure, unauthorized writes, account or dependency compromise, or an unreproducible release.

P0

Project APIs bypass authorization

  • projects.list paginates all projects without authentication or tenant filtering.
  • projects.update patches scalar fields and replaces recipe contents without an identity or ownership check.
  • projects.remove cascades deletion without authentication.
  • createNewVersion and duplicate clone any project ID without authorization.

P0

Core domain modules expose unauthenticated CRUD

Nine Convex modules with public APIs contain no authentication marker at all: comments, equipment, i18n maintenance, inventory, lab reports, project ingredients, recipe phases, regulatory imports, and step dependencies. This is a systemic boundary problem; adding checks only in the UI will not fix it.

Evidence: rd/formulation-lab/convex/ · 9 of 27 public-API modules lack getUserIdentity, getAuthUser, or requirePermission

P0

Spreadsheet writes treat anonymous callers as “system”

updateCell, resize, and clearRange load a project step and write it without checking project access. Missing identity is recorded as system, which hides the authorization failure in audit metadata.

Password signup does not require email verification. The direct auth dependency is pinned at 1.5.3 despite advisories patched in 1.6.11–1.6.13. The repository has no tests that call Convex functions under anonymous, wrong-team, viewer, editor, and admin identities.

rd/formulation-lab/.env is tracked and has a long commit history. The current file contains deployment identifiers and service URLs. These values may be public by nature, but tracking the file makes future secret leakage likely and complicates environment separation.

05 / Remediation roadmap

A short path to a controlled beta.

Fix the trust boundary first, then make every release prove it. Performance and maintainability follow once correctness is protected by tests.

Before deploy

Close the data boundary

  1. Create shared Convex access helpers for authenticated user, team membership, project viewer/editor, and explicit system permissions.
  2. Apply them to every public query and mutation. Derive actor and ownership fields server-side; do not accept userId, author, resolver, or tenant identity from the client.
  3. Make administrative imports and maintenance functions internal. Make missing secrets fail closed.
  4. Require secure, expiring share/invite tokens; check expiry, active state, entity ownership, invite email, and role escalation.
  5. Remove the tracked .env, inspect its history, and rotate anything secret that was ever committed.
Next 2–3 days

Make security executable

  1. Add backend tests for anonymous, wrong-user, wrong-team, viewer, editor, admin, expired-link, and replay cases across each entity family.
  2. Upgrade Better Auth and affected transitive packages, regenerate the lockfile, rerun the full auth suite, and require a clean production audit or an explicit, scoped exception.
  3. Enable email verification in non-local deployments and document session/cookie/origin configuration.
  4. Provision Playwright Chromium in CI and separate pure logic tests from browser E2E so failures are clear.
Next week

Restore the release path

  1. Add one root check command that runs formatting/lint, typecheck, localization checks, unit tests, E2E, build, and dependency audit with correct package scopes.
  2. Add protected CI with frozen install, cache, Playwright browser provisioning, artifacts, and required status checks.
  3. Choose and check in one deployment path. Define build/start commands, immutable artifact versioning, health checks, rollback, and environment ownership. Remove stale GHCR/Coolify text if that path stays retired.
  4. Add error monitoring with release IDs and source maps, structured server logs, alert ownership, and a tested backup/restore procedure for Convex data and stored files.
Before scale

Bound cost and change risk

  1. Use Convex Insights against the intended deployment. Fix measured hot paths plus clearly unbounded scans, starting with inventory list enrichment and ingredient dependency scans.
  2. Lazy-load route-level lab screens and PDF/grid-heavy code. Set a main-route JavaScript budget and test it in CI.
  3. Split the 2,252-line formulation page and large backend modules along stable feature and authorization boundaries.
  4. Run a staging release, cross-tenant penetration test, restore drill, rollback exercise, and production smoke test before the go/no-go review.
Controlled beta entry

All P0/P1 findings closed; access-control matrix tests green; clean build, typecheck, lint, E2E, and dependency gate; one reproducible staged deployment with rollback and restore evidence.

Production entry

Beta criteria plus runtime monitoring, alert ownership, measured performance budgets, backup/restore drill, incident runbook, and a completed cross-tenant security review.
