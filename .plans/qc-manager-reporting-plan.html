Implementation design · Quality control

Manager reporting without changing existing QC pages

A new manager-only page at /quality/reports containing seven decision-focused reports. The plan uses existing inspection, review, lab, and sample data first. Final-product lab reports are connected to sample submissions by a normalized batch-number match and retain the sample ID as the durable relationship.

Goal and agreed premises

The manager needs a separate place to find exceptions, trends, workload constraints, and audit evidence. Managers should not have to inspect individual records to discover where action is needed.

  1. Separate delivery: add a new route and navigation item. Do not replace or repurpose /reports, /quality/production-line-records, /quality/lab-samples, or their detail pages.
  2. Decision support: every report must end in a drill-down list that tells the manager which record, product, line, batch, or person needs attention.
  3. Existing data first: release one uses stored inspection readings, checks, evidence, workflow events, lab reports, test results, and batch-linked sample submissions. Derived reporting tables may be added, but no QC capture screen is changed.
  4. Fair team reporting: show workload, timeliness, and workflow outcomes with sample sizes. Do not create an inspector score or rank people by raw failure counts.
Data truth: all 22 compliance checks must be checked before an inspection can be submitted. An unchecked item means “not yet confirmed,” not “failed.” Release one must never label unchecked draft items as defects. Confirmed compliance failures require a later structured finding model.

Approach decision

Approach A: Small dashboard

One overview with KPI cards and a filtered inspection table.

Effort: low. Risk: low.

Rejected because: it helps daily review but does not satisfy the request for an implementation case and exact contents for each report.

Approach B: Modular report suite

One manager route with seven tabs, shared filters, bounded reporting queries, exports, and record drill-down.

Effort: medium. Risk: medium.

Selected because: it covers every stated manager decision while preserving current operational pages.

Approach C: External analytics warehouse

Replicate data into a BI system and build dashboards there.

Effort: high. Risk: high.

Rejected because: the current scope is organization-level operational reporting, and Convex already contains the required source records.

No external landscape search was run. The plan is based on the repository’s actual data model and workflow. The main risk is missing an organization-specific regulatory export format.

New page structure

Add /quality/reports to the Quality workspace navigation as QC reports. The route is visible only to users with review_production_checks; organization administrators retain access through full_access.

Global controls

  • Date range, default last 30 calendar days in the organization timezone.
  • Product, production hall, department/line, QC inspector, record status, and specification version.
  • Filters are stored in URL search parameters so a manager can bookmark a view.
  • Interactive ranges are capped at 90 days. Longer periods use CSV export jobs or later daily aggregates.

Report navigation

Tabs: Overview, Measurements, Readiness, Products & lines, Workflow & team, Audit, Laboratory.

Every tab shows the active date range, last refresh time, applied filters, an explanatory metric note, and a CSV export button where tabular data exists.

Shared display rules

  • Use the organization timezone from productionLineSettings.timezone for day and hour boundaries.
  • Show numerator and denominator beside every percentage, for example “8.3% · 5 of 60 records.”
  • Do not rank comparison rows until they contain at least 10 inspections. Mark smaller groups “low sample.”
  • Clicking a production record opens the existing detail route. Clicking a lab report opens the existing lab report detail route.
  • Use Recharts for trends and control charts, and LabDataGrid for sortable drill-down tables.

1 Daily QC control report

Case: this is the first screen a production manager opens. It answers “what needs action now?” without forcing the manager to open every pending record.

Exact information shown

Inspections today

Count of records whose inspectionAt falls within today in the organization timezone, split by status.

Pending queue

Count pending review, median pending age, and oldest pending age. No arbitrary “overdue” label is used until an SLA is configured.

Out-of-limit records

Count of submitted, returned, or approved records containing at least one reading where withinLimit = false.

Return decisions

Review decisions marked returned today, with the return note available in the drill-down.

  • Queue chart: inspection count by hour and status for today.
  • Exception table: serial, product, hall, department, printed batch code, inspector, inspection time, out-of-limit reading count, affected reading names, status, and pending age.
  • Action order: out-of-limit pending records first, then oldest pending records, then returned records awaiting resubmission.

Metric definitions

pending age = now - most recent submittedAt
out-of-limit record = outOfLimitReadingCount > 0
returned awaiting work = current status == "returned"

Available now inspection time, product, hall, department, batch code, inspector, status, readings, and review events. Derived pending age and exception ordering.

Acceptance criteria

  • A manager can identify all currently pending out-of-limit records in two clicks or fewer.
  • Counts match the record list for the same organization and status.
  • Today’s boundary changes correctly for a non-UTC organization timezone.

2 Measurement conformance and drift report

Case: a single approved record can still contain an out-of-limit measurement. This report detects process drift by parameter, product, specification version, line, and time before repeated variation becomes a larger batch problem.

Exact information shown

  • KPI cards for total readings, in-limit readings, out-of-limit readings, records with any out-of-limit reading, and record conformance rate.
  • A parameter selector for pour weight, additive weight, chocolate temperature, coated piece weight, and carton weight.
  • A time-series control chart showing each actual value plus its stored minimum, target when present, and maximum. Never use the current specification for an old reading; use the limits snapshotted on that reading.
  • A daily conformance trend and a table grouped by product, hall, department, parameter, and specification version.
  • An outlier table with serial, batch, product, value, unit, minimum, target, maximum, signed distance beyond the nearest limit, inspector, and inspection time.

Metric definitions

reading conformance rate = within-limit readings / all readings
record conformance rate = records with zero out-of-limit readings / records with readings
distance beyond limit = value < min ? value - min : value > max ? value - max : 0

Optional capability statistic: show Cpk only when there are at least 30 readings for one product, one parameter, and one specification version. Compute sample standard deviation and min((USL - mean)/(3s), (mean - LSL)/(3s)). Label it “observed capability,” not a release decision, and hide it when standard deviation is zero or the sample is too small.

Available now actual values, units, snapshotted limits, targets, parameter keys, product, hall, line, inspector, and specification version.

Acceptance criteria

  • A point outside its stored limits appears in both the chart and outlier table.
  • Changing specification version never combines incompatible limits in one Cpk calculation.
  • Every aggregate percentage exposes its count and denominator.

3 Inspection readiness and evidence report

Case: managers need to find inspections stalled before submission and evidence gaps that could block review or an audit. This is a completeness report, not a defect report.

Exact information shown

  • Counts of draft and returned records, median draft age, and oldest unchanged record.
  • Readiness breakdown: missing batch-label photo, missing confirmed batch code, missing required measurements, or incomplete compliance confirmations.
  • Evidence coverage cards: records with photo, records with confirmed code, records with all required readings, and records with all 22 checks confirmed.
  • Stalled record table: serial, product, hall, department, owner, created time, last updated time, current status, and each missing requirement.
  • Compliance confirmation matrix by check group: packaging/product, materials/people, environment/safety, and maintenance. Values are “confirmed,” “awaiting confirmation,” and “not applicable only after phase-two support.”

Metric definitions

evidence coverage = records satisfying requirement / records in selected set
draft age = now - createdAt
stalled age = now - updatedAt
readiness = same getProductionLineSubmissionReadiness rules used by submission

Never display: “compliance failure rate” from unchecked boxes. Current data cannot distinguish failure from unfinished work.

Available now photo/code confirmation, checks, required reading counts, record timestamps, owner, and status. Later capture true failed checks, severity, notes, photos, and corrective actions.

Acceptance criteria

  • The readiness reason matches the mobile submission blocker for the same record.
  • No unchecked item is described as a defect, nonconformance, or failed inspection.
  • A manager can open the existing production record detail directly from each row.

4 Product, hall, and line comparison report

Case: this report locates recurring process risk. It answers whether variation is concentrated in a specific product, production hall, department, or specification version.

Exact information shown

  • Toggle grouping by product, hall, department/line, or specification version.
  • For each group: inspection count, approved count, returned count, records with out-of-limit readings, reading conformance rate, first-pass approval rate, and median review time.
  • Heatmap with group rows and the five reading parameters as columns; each cell contains out-of-limit count and conformance percentage.
  • Eight-week trend for the selected group versus the organization baseline.
  • Drill-down table containing the exact records behind a selected cell.

Metric rules

group out-of-limit rate = group records with OOL / group records with readings
baseline delta = group rate - organization rate for the same date range
first-pass approval = records whose first review decision was approved / reviewed records

  • Sort by highest actionable rate only when sample size is at least 10; otherwise sort low-sample rows after comparable groups.
  • Do not combine product versions with different specification versions in a capability calculation.
  • Show raw count beside rate to prevent a small group from appearing more important than a large group.

Available now all required grouping dimensions and outcomes. Not available production quantity, so the report cannot calculate defects per thousand units.

Acceptance criteria

  • Selecting a heatmap cell produces a drill-down whose count equals the cell count.
  • Low-sample groups are visibly marked and are not given a red/green performance rank.
  • The organization baseline uses the same filters and date range as the selected group.

5 Review workflow and QC workload report

Case: managers need to see whether delays come from inspection preparation, the review queue, repeat returns, or uneven assignment. The report manages flow; it does not produce a staff league table.

Exact information shown

  • Workflow cards: submissions, review decisions, approvals, returns, median submission-to-review time, 90th-percentile review time, current pending queue, and oldest pending item.
  • Funnel: created → submitted → approved or returned → resubmitted → final approval.
  • Inspector workload table: assigned inspections, submitted inspections, current drafts, current returned records, reviewed sample size, first-pass approvals, return count, and median create-to-submit time.
  • Reviewer workload table from record events: decisions completed, approvals, returns, and median submission-to-decision time.
  • Daily queue trend and review-time distribution rather than a misleading single average.

Metric definitions

create-to-submit = first submission time - record.createdAt
review time per cycle = reviewedAt - submittedAt
first-pass approval = first review decision == approved
return rate = returned decisions / all review decisions
P90 = nearest-rank 90th percentile of completed review-cycle durations

Fairness rule: never label an inspector “best” or “worst.” Display product mix, hall mix, and reviewed sample size beside outcomes. Returns are workflow signals because reviewer notes and assignment difficulty affect them.

Available now record owner/QC user and timestamped submitted, approved, and returned events. Derived review cycles, percentiles, and first-pass status.

Acceptance criteria

  • A returned and resubmitted record creates two review cycles and only one first review decision.
  • Pending cycles are excluded from completed review-time medians but included in queue age.
  • No staff row is ranked without its workload and sample-size context.

6 Batch traceability and audit register

Case: this report assembles the evidence already spread across production records, readings, photos, specifications, and review events. It supports internal audits and batch investigations.

Exact information shown

  • Searchable register by printed batch code, form serial, product, date, hall, department, QC officer, status, and specification version.
  • Evidence columns: label photo present, code confirmed, required readings complete, compliance checks complete, reviewer decision present, return note count, and final status.
  • Record audit drawer: organization, serial, batch, product, hall/line, inspection time, inspector, captured label photo, printed code, specification ID/version, every reading with stored limits, all check confirmations, and the ordered event history with actor and revision.
  • Single-record PDF packet using @react-pdf/renderer; CSV exports for the register and readings.
  • A SHA-256 digest of the exported packet payload can be printed in the footer for later integrity comparison. It is an export digest, not a digital signature.

Batch-to-sample relationship

For organization reports, the sample productionNumber and report lotNumber use the same canonical DDMMYYN batch format. Report creation validates the selected sample belongs to the same organization and product, is a final-product sample, and has the same normalized batch number. The report then stores sampleSubmissionId, so reporting uses an ID relationship after batch-number matching rather than repeating a text join.

If a product has more than one sample submission for the same batch, the report must show each sample number, sampling time, and location and retain the specifically selected sample ID. The audit packet displays both the canonical batch number and linked sample number.

Available now all production inspection evidence, event history, canonical batch number, linked sample number, and linked lab report evidence. Later capture an authorized digital signature for exported audit packets.

Acceptance criteria

  • The audit event order matches productionLineRecordEvents.createdAt and shows every revision.
  • The PDF contains the same values and stored limits as the existing record detail.
  • Possible text matches are clearly separated from verified relationships.

7 Laboratory quality report

Case: production checks show process conditions, while lab results show whether the sampled finished-product batch met analytical specifications. The batch-number relationship lets managers follow a sample from collection into its lab report and find sampled batches that still have no report.

Exact information shown

  • Lab report cards: total reports, approved, pending, failed, reports with any out-of-spec test, and overall test conformance rate.
  • Sample coverage cards for final products: sampled batches, unique linked samples, samples without a linked report, sample-to-report creation time, sample-to-approval time, and report-to-approval time.
  • Parameter table: test count, in-spec count, out-of-spec count, conformance rate, actual-value range, and affected products.
  • Product table: reports, failed reports, reports containing out-of-spec tests, top affected parameters, and latest report date.
  • Pending report list: report ID, linked sample number, product, canonical batch number, sample time, sample location, lead chemist, report date, age since record creation, and open action.
  • Unreported final-product sample table: sample number, product, canonical batch number, sample location, sampled time, sample age, and submitter. Each row opens a report-page drawer with the stored sample details; no separate sample-detail route currently exists.
  • Batch drill-down: sample metadata, all reports linked to that sample, report status, test conformance, signed approval time, and a link to each existing report detail page.
  • Raw-material sample intake remains a separate volume section because the current report workflow only permits links to final-product samples.

Metric definitions

test is in spec = actualValue >= min AND actualValue <= max
test conformance rate = in-spec tests / all tests
report has OOS = at least one child test is outside min/max
sample coverage = unique final-product samples with at least one linked report / final-product samples in the sampledAt cohort
sample-to-report time = labReport._creationTime - sample.sampledAt
sample-to-approval time = labReport.signedAt - sample.sampledAt
report-to-approval time = labReport.signedAt - labReport._creationTime
pending age = now - labReport._creationTime

Cohort rule: coverage uses samples whose sampledAt falls inside the selected range, even if their reports were created later. Count each linked sample once when several reports reference it. Report totals remain report counts.
Still unavailable: received-to-tested and tested-to-approved stage times. The batch link provides end-to-end sample and approval timing, but the intermediate laboratory workflow timestamps are not stored.

Available now report status, product, canonical batch number, linked sample ID and number, sampling time, sample location, lead chemist, tests and limits, submitter, report creation time, and signed approval time. Later capture received, testing-started, testing-completed, and technical-review timestamps.

Acceptance criteria

  • Report-level OOS is derived from child test values, not inferred from the manually assigned report status.
  • Pending report age uses a timestamp, not locale-formatted report date text.
  • A linked report is included only when sampleSubmissionId resolves inside the same organization and its normalized lot number equals the sample production number.
  • A sample with two linked reports counts once in sample coverage and twice in report totals.

Review cycle facts

Add qualityReviewCycles, one document per submission cycle. On submission insert a pending cycle with record, organization, cycle number, QC user, product, hall, department, and submittedAt. On review patch that cycle with reviewer, reviewedAt, decision, note-present flag, and durationMs.

Indexes: by_recordId_and_cycleNumber, by_organizationId_and_submittedAt, by_organizationId_and_qcUserId_and_submittedAt, and by_organizationId_and_reviewerId_and_reviewedAt.

Consistency rules

  • Create and update derived facts in the same mutation that changes the source record. Do not schedule eventual updates.
  • saveReading adjusts summary counts from the previous and next withinLimit values. Photo, code, check, submit, and review mutations update only their owned summary fields.
  • Backfill historical summaries and cycles with @convex-dev/migrations. Derive cycles by ordering record events and pairing each submission with the next approval or return.
  • Add invariant tests comparing a summary with its source record, readings, checks, and events.
  • Return only explicit validators. Do not expose unrestricted documents to the client.

Laboratory summary and batch linkage

Add qualityLabReportSummaries with labReportId, sampleSubmissionId, sampleNumber, organization, project, product name, canonical batch number, sample location, sampledAt, report status, lead chemist, sample type, report creation time, signedAt, total test count, in-spec count, out-of-spec count, and bounded out-of-spec parameter names. Create it in labReports.create, update approval fields in labReports.updateStatus, remove it in labReports.remove, and backfill existing reports.

Link creation rules

  1. Normalize the report batch input with the existing normalizeProductionNumber helper. It removes whitespace, validates DDMMYYN, and rejects invalid calendar dates.
  2. Limit candidates to the same organizationId, the run’s projectId, and sampleType = "final_product". Use by_organizationId_and_productionNumber for batch lookup and then apply the product/type checks.
  3. If exactly one candidate exists, select it automatically. If several samples share the batch, require the user to choose by sample number, sampled time, and location. If none exists, block organization report creation and direct the user to submit the sample first.
  4. Store both the canonical value in labReports.lotNumber and the durable foreign key in labReports.sampleSubmissionId. Use the foreign key for report queries and the batch value for validation, search, and audit display.
  5. Use labReports.by_sampleSubmissionId to list all reports for one sample. Do not assume the relationship is one-to-one.

Historical backfill

For every organization report without sampleSubmissionId, normalize lotNumber, find final-product samples in the same organization and project with that production number, and link only a unique match. Record zero-match and multiple-match cases for manual resolution. Never choose a sample by date proximity alone.

Loading and failure behavior

  • Load only the active tab’s main query. Do not subscribe to all seven reports at once.
  • Debounce text filters and keep chart queries bounded. Audit rows use Convex pagination.
  • Show “No records in this range” separately from query failure.
  • When a derived summary is missing during rollout, exclude it from percentages and show the number of records still awaiting backfill.
  • Exports state the organization, filters, timezone, generation timestamp, and row count.

Rollout, assignment, and verification

Delivery sequence

  1. Widen: add optional derived summary/cycle tables and staged indexes. Add query validators and pure metric helpers.
  2. Maintain: update production and lab mutations so every new or changed record maintains its reporting facts transactionally.
  3. Backfill: run idempotent migrations for inspection summaries, review cycles, legacy batch-to-sample links, and lab summaries. Record linked, no-match, ambiguous, processed, and failed counts.
  4. Activate: remove staged flags after index backfill, deploy the reporting queries, and compare report totals to source queries.
  5. Expose: add the manager-only route, Quality sidebar item, seven report tabs, drill-down, localization, and exports.

Test matrix

  • Backend: organization isolation, manager permission, date-bound validation, timezone day keys, OOL math, first-pass logic, resubmission cycles, percentile math, and lab OOS derivation.
  • Migration: rerun safety, missing event pairs, records with no readings, unique batch matches, zero batch matches, ambiguous same-batch samples, legacy lab reports without organization, and summary/source parity.
  • Frontend: route invisibility for QC officers, tab filters, URL restoration, empty states, low-sample labels, record drill-down, CSV quoting, PDF content, dark mode, English, Arabic, and RTL.
  • Performance: seed 90 days of hourly records across both halls and confirm every interactive query stays below Convex read limits and renders within the agreed target.
Concrete next assignment: implement the reporting fact schema, staged indexes, pure metric helpers, and backfill tests before building charts. The page should not be connected until parity tests prove the derived counts match existing source records.
