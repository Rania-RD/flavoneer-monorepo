Replace one active paper workflow end to end

The first release digitizes the production-line monitoring form without building a generic form builder. The QC team enters the record in the Expo mobile app during production. The record survives app restarts and lost connectivity. The production manager reviews the submitted record and adds the second signature from the existing web workspace.

In scope

02 · What was agreed

Premises and operating signals

Premises

  1. QC completes the form in the mobile app while production is running.
  2. Production management reviews the submitted record.
  3. QC and production both sign the same record revision.
  4. Each modification is saved locally before synchronization is attempted.
  5. Connectivity can disappear during entry, so the app cannot treat Convex as the draft store.
  6. Approved records cannot be silently edited or deleted.

Signals

  • The company already uses a concrete paper form, which is stronger evidence than a hypothetical request.
  • The responsible people and approval handoff are named.
  • The required device and moment of entry are named: mobile during production.
  • The offline and autosave requirements came from the expected operating environment.
  • The current mobile app has shared Convex and Better Auth wiring but no domain workflow yet.

External landscape check

03 · Selected approach

Dedicated production-line form

Decision: build a typed form and workflow for one production use case. Keep the storage boundaries clean enough to extract shared primitives after the team has observed real mobile usage.

Why this path

  • It gets one active workflow into factory use faster.
  • Fixed fields support stronger validation and a clearer mobile layout.
  • Offline sync is already a large engineering surface and should be tested before arbitrary form schemas are added.
  • Observed use will reveal which primitives are actually shared by the later forms.

Effort and risk

Effort: 5–7 engineering weeks for one engineer, including a controlled pilot.

Risk: medium. The highest risks are offline conflict handling, auth expiry, signature meaning, and operational adoption.

Rejected alternatives

Configurable compliance-form engine

Rejected for the first release because arbitrary schemas, repeatable sections, migrations, and offline rendering would delay the first factory form and increase the test surface before mobile behavior is observed.

Production-session event timeline

Rejected because it changes the familiar operating model. It may be a better later UX, but the first pilot should preserve the recognizable form and approval process.

04 · Operational workflow

One record, five controlled states

Editable Draft QC enters data. Every change saves locally and queues synchronization.
Queued Submission queued QC confirms the record offline. Final submission waits for a valid online session.
Review Production review QC revision is frozen. Production can approve or return it with a reason.
Editable Returned QC corrects the record. The old signed revision remains in the audit history.
Locked Approved Production co-signs. Direct edits and deletion are blocked.

Step-by-step usage

  1. QC signs in and opens the Quality tab in the mobile app.
  2. QC selects “New production-line record.” The app creates a UUID-backed local draft immediately.
  3. QC selects the department or line and product from cached reference data. A product-name snapshot is stored so the record stays readable if names change later.
  4. QC enters one or more timed measurement rounds and completes all conformity checks.
  5. Any non-conforming check requires a note and immediate action before submission.
  6. The app displays “Saved on device,” “Waiting to sync,” or “Synced” independently from the form validation status.
  7. QC reviews a summary, confirms identity, and taps “Sign and submit.” If offline, the action is queued and clearly marked as not yet submitted to the workspace.
  8. On reconnect, the app syncs the latest draft, then sends the queued submission. If auth expired, it asks QC to sign in without removing the local record.
  9. The production manager opens the web review queue, checks data and deviations, then approves or returns the record with a required reason.
  10. Approval creates the second signature event, locks the revision, and makes the official PDF available.
Important distinction: “Saved on device” does not mean “submitted.” The UI must never show an offline queued signature as a completed server approval.

Navigation

07 · Offline architecture

SQLite draft, durable outbox, idempotent Convex sync

Mobile form

Typed state and Zod validation. Every edit calls the local repository.

→

SQLite

Draft snapshot, reference cache, sync queue, revisions, and local error state.

→

Convex

Workspace authority, workflow, signatures, audit events, queries, and web review.

Local database

Add expo-sqlite for Expo SDK 57. SQLite persists across application restarts. Enable WAL mode. Evaluate SQLCipher during the first implementation spike because enabling it changes native configuration and requires a new mobile binary.

Local tablePurposeKey fields
production_line_drafts One current JSON snapshot per local record. client_record_id, owner_user_id, payload_json, client_revision, server_revision, status, timestamps
production_line_outbox Durable sync and workflow operations. operation_id, client_record_id, operation_type, client_revision, payload_json, attempts, retry time, last error
quality_reference_cache Departments, products, runs, shifts, and workspace metadata for offline selection. cache_key, payload_json, fetched_at, expires_at
local_schema_migrations Deterministic local database upgrades. version, applied_at

Save transaction

  1. Validate and normalize the changed field locally.
  2. Increment clientRevision.
  3. In one SQLite transaction, write the complete draft snapshot and upsert one coalesced sync_draft outbox row.
  4. Only after the transaction commits, show “Saved on device.”
  5. Debounce network work, not local durability. Rapid edits should replace the queued draft snapshot rather than create one request per keystroke.

Sync worker

  1. Wake on app start, sign-in completion, foreground resume, manual retry, and network reachability changes.
  2. Process one record at a time. Send the most recent coalesced draft before workflow operations such as submission.
  3. Call an idempotent Convex mutation with clientRecordId, clientRevision, baseServerRevision, and the complete bounded snapshot.
  4. On success, store the returned Convex ID and server revision locally, then remove only the acknowledged outbox operation.
  5. On a transient error, keep the row and retry with capped exponential backoff and jitter.
  6. On auth failure, pause the queue and request sign-in.
  7. On stale revision, mark the draft as conflicted. Never use silent last-write-wins.

Conflict boundary

The pilot supports one editable owner and one primary device per draft. A second device can view a synced draft but cannot take ownership while offline. An online “Take over editing” action may be added after pilot feedback. This rule removes most multi-device merge cases.

  • If the same clientRevision and content arrive twice, the server returns the previous acknowledgement.
  • If an older client revision arrives, the server ignores it and returns the latest server revision.
  • If the client is based on an old server revision and its content differs, the server returns a conflict.
  • The conflict UI preserves both copies. QC can duplicate the local values into a new corrected draft, but cannot overwrite a submitted or approved revision.
Reason for a custom outbox: Convex reconnects its WebSocket and retries outstanding online mutations, but the product requirement needs a durable local record, explicit queue state, app-restart recovery, and controlled ordering between draft sync and signature submission.

Data invariants

  • clientRecordId is generated once on device and is unique within a workspace.
  • Only draft and returned records accept draft synchronization.
  • A record cannot enter production review until all required fields and checks are valid.

11 · Security and record integrity

Authentication is necessary; immutable events make signatures meaningful

Mobile device

  • Keep Better Auth tokens in Expo SecureStore, as the current app does.
  • Store the SQLite encryption key in SecureStore if SQLCipher is enabled.
  • Bind local drafts to workspace and user IDs. Do not expose one user's queue to another user.
  • Do not delete unsynced drafts during sign-out. Pause and hide them until the original user returns.
  • Do not log field values, notes, product secrets, or signatures to Bugsink.

Server

  • Derive actor identity and permissions on every mutation.
  • Store server timestamps for authoritative workflow events.
  • Keep client timestamps to explain offline chronology, but do not trust them for authorization.
  • Reject updates to submitted, approved, voided, or wrong-workspace records.
  • Keep approved snapshots, signatures, events, and amendments append-only.

Signature policy

A drawn or uploaded signature image is presentation data. The authoritative signature receipt contains the authenticated user ID, name and role snapshot, signature purpose, signed revision, server timestamp, and immutable snapshot reference. An offline QC tap creates a queued intent. The server creates the signature only after revalidating auth, permission, record state, and content revision.

Deletion and correction

  • A local-only draft may be discarded after confirmation.
  • A synced draft is discarded through a server mutation that records the event.
  • A submitted record is returned, not reopened silently.
  • An approved record is never edited in place. Corrections use an amendment or a replacement record linked to the original.
  • Admin voiding changes status and records a reason. It does not physically delete the record.
Regulatory boundary: this design follows common record-integrity controls, but retention periods, signature wording, device controls, and whether specific regulations apply must be approved by the company's quality and legal owners before paper is retired.

13 · Verification

Test the failure paths before the happy-path pilot

Local persistence tests

  • Every field change updates the local snapshot and increments the client revision.
  • Draft and outbox writes commit atomically.
  • App termination immediately after entry does not lose the last committed field.
  • Local schema migrations preserve existing unsynced drafts.
  • Signing out hides but does not delete an unsynced queue.

Sync state-machine tests

  • One hundred rapid edits coalesce to the latest correct snapshot.
  • Duplicate mutation delivery is idempotent.
  • Network loss during acknowledgement does not create duplicate records or signatures.
  • Queue order always syncs the latest draft before submission.
  • Expired auth pauses and resumes without removing queued data.
  • Network flapping respects retry limits and never spins continuously.
  • A stale server revision produces a visible conflict instead of overwriting data.

Backend authorization tests

  • QC can update only editable records assigned to that user and workspace.
  • Production reviewers cannot edit field content.
  • Users without review permission cannot approve or return a record.
  • Cross-workspace reads and writes fail.
  • Approval fails if the QC-signed revision is no longer current.
  • Approved records reject patch and delete operations.
  • Void and amendment actions require reasons and create events.

Mobile behavior tests

  • Arabic RTL order, labels, numeric fields, and validation render correctly on Android and iOS.
  • All controls meet practical touch-target size for factory use.
  • The form remains usable with airplane mode enabled before opening it.
  • A local draft reopens at the correct step after app restart.
  • Queued submission is distinguishable from server-confirmed submission.
  • Non-compliant and not-applicable checks require the correct explanations.

Web and document tests

  • Review queue filters and pagination return only the active workspace.
  • Return requires a reason and reopens only the correct QC workflow.
  • Approval locks the record and writes the production signature once.
  • Arabic PDF text, tables, signatures, and page breaks render correctly.
  • PDF content continues to match the approved snapshot after profile names or signatures change.

Operational pilot scenarios

  • Start online, lose network mid-form, close the app, reopen offline, complete, reconnect, and approve.
  • Start fully offline using cached reference data, then sync after the production period.
  • Queue a submission, allow auth to expire, reauthenticate, then verify one submission and one signature.
  • Return a signed record, correct it on mobile, resubmit, and verify both signed revisions remain visible.

14 · Delivery plan

Five build milestones and one controlled pilot

Confirm field meanings and units with QC. Add additive Convex schema and validators. Add SQLite, migrations, repository, and outbox. Prove one field survives app termination and syncs idempotently.

Week 2: complete mobile form

Build Quality navigation, record list, header, measurement rounds, conformity groups, deviations, notes, Arabic translations, validation, and save-state UI.

Exit: QC can complete and reopen the full form in airplane mode.

Week 3: sync hardening and QC submission

Implement reconnect triggers, coalescing, retry policy, auth pause, conflict handling, immutable snapshots, and queued QC submission.

Exit: network-loss and duplicate-delivery tests pass.

Week 4: production review

Add permissions and roles, web review queue, detail view, return, approval, production signature, audit timeline, and approved lock.

Exit: one record completes QC entry through production approval.

Week 5: PDF, amendments, and release gates

Add Arabic PDF output, approved amendments, tenant-isolation tests, mobile failure-path tests, web Playwright coverage, observability, and operating documentation.

Exit: release candidate passes the full repository gate and the pilot checklist.

Weeks 6–7: shadow pilot and corrections

Run the app beside the paper form on one line and one shift. Compare every record, observe QC without coaching, fix blockers, and obtain written quality/production approval before considering paper retirement.

Exit: agreed pilot threshold is met with no missing or irreconcilable records.

Distribution

  1. Deploy additive Convex tables and functions. Existing records and flows remain untouched.
  2. Ship the web review routes behind the new permissions.
  3. Create a new EAS mobile binary because adding Expo SQLite and optional SQLCipher changes native configuration. Hot Updater alone is not enough for this first release.
  4. Install the release on a small set of managed factory devices.
  5. Preload the workspace and reference cache while online before the first shift.
  6. Run paper and mobile in parallel during the pilot.
  7. After the native dependency is present in the installed binary, compatible JavaScript fixes can use the existing Hot Updater production channel.

Operational metrics

Collect metadata only, never field values:

  • Local autosave failure count.
  • Outbox age, queue length, retry count, and sync latency.
  • Auth-paused and conflict counts.
  • QC submission-to-production-review time.
  • Return rate and non-conformity count by form, without note contents.
  • Crash-free form sessions and PDF generation failures.

15 · Release definition

Acceptance criteria

  • An authenticated QC user can create the form with no internet when reference data has been cached.
  • Every visible edit is present after force-closing and reopening the mobile app.
  • The app always distinguishes local save, queued sync, server sync, queued submission, and confirmed submission.
  • Reconnect synchronizes the newest draft exactly once, even after duplicate attempts.
  • A complete form includes the required header, at least one measurement round, all 22 conformity checks, and notes required by failed checks.
  • QC submission creates a signature event tied to an immutable revision.
  • The production manager can return with a reason or approve with the second signature.
  • No user can directly edit or delete an approved record.
  • An approved correction preserves the original and identifies old value, new value, reason, requester, reviewer, and times.
  • The web workspace can search and filter records by date, status, product, batch, and department.
  • The official Arabic PDF matches the approved snapshot and includes both signature receipts.
  • Cross-workspace access tests fail closed.
  • The pilot can reconcile every mobile record with its parallel paper record.

16 · Risks and open decisions

Resolve these before paper retirement

RiskEffectMitigation
Business limits are not supplied The app cannot safely decide whether temperature or weights are within specification. Use structural validation only in the pilot. Get product-specific limits and units from QC before automatic pass/fail logic.
Signature policy is not legally reviewed A digital sign-off may not meet the company's applicable policy or jurisdiction. Store strong signature receipts now. Obtain quality/legal approval for wording, reauthentication, retention, and device controls.
Multiple devices edit one draft Offline changes cannot be safely merged field by field. Use one editable owner/device in the pilot and explicit conflicts. Add takeover only after observing the need.
Reference cache is stale A renamed or closed product may be selected offline. Store ID plus name snapshot, show cache age, reconcile on sync, and allow production review to return the record.
OS background limits Sync may not run until the app returns to the foreground. Promise foreground/reconnect sync only. Show queue age and instruct QC to confirm sync before ending the shift.
Local device loss Unsynced drafts may exist only on one device. Use encryption, managed devices, frequent sync when reachable, clear ownership, and an end-of-shift pending-queue check.
Paper layout is treated as mobile UX A wide table becomes slow and error-prone on a phone. Use vertical cards and grouped checks while preserving familiar section names and official PDF layout.

Open questions

  1. What are the allowed units and acceptable limits for each product's weights and chocolate temperature?
  2. Does one form represent a shift, one batch, one run, or one inspection time?
  3. How many measurement rounds normally occur on one form?
  4. Which devices and operating systems will be used on the production floor?
  5. How long must approved records be retained, and who can void or amend them?
  6. Must production managers be able to review and sign from mobile in the first release, or is web review sufficient?
  7. Should QC re-enter a password or device biometric at signature time?
  8. Are photos required for non-conformities in the pilot?

17 · The assignment

Build one thin offline vertical slice first

Concrete next action: implement one production-line draft containing the header and one measurement value, save it atomically to SQLite, terminate and reopen the app to prove recovery, reconnect and sync it through an idempotent productionLineRecords.syncDraft mutation, then display the saved record in one read-only web page.

Do not build all form sections before this slice passes app-restart, duplicate-delivery, expired-auth, and workspace-isolation checks. That slice validates the hardest architectural decision while the UI and schema are still cheap to change.
